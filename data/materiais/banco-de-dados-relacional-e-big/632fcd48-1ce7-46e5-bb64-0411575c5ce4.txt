===== PAGINA 5 =====
O que motivou o surgimento do NoSQL?
Com a ascensão da era digital, empresas começaram a lidar 
com volumes de dados sem precedentes, além de formatos 
altamente variados e com alta taxa de atualização. Nesse 
cenário, os bancos de dados relacionais passaram a enfrentar 
limitações estruturais e de desempenho. A rigidez dos 
esquemas, o alto custo de escalabilidade vertical e a 
dificuldade em lidar com dados semiestruturados 
impulsionaram o surgimento de alternativas mais flexíveis e 
escaláveis: os bancos de dados NoSQL.

===== PAGINA 6 =====
O que significa NoSQL?
A sigla NoSQL, embora inicialmente interpretada como "Not
Only SQL", reflete uma filosofia de bancos de dados que não 
dependem exclusivamente do modelo relacional tradicional. 
Esses bancos adotam modelos de armazenamento 
alternativos que permitem maior maleabilidade estrutural, 
melhor desempenho em ambientes distribuídos e capacidade 
de lidar com dados heterogêneos — características 
fundamentais no contexto do Big Data e de sistemas 
modernos.

===== PAGINA 7 =====
A diferença começa nos princípios
Enquanto os bancos relacionais seguem o modelo ACID, 
garantindo Atomicidade, Consistência, Isolamento e 
Durabilidade, os bancos NoSQL seguem o modelo BASE: 
Basicamente Disponível, Estado Flexível (Soft-state) e 
Consistência Eventual. Essa mudança de paradigma permite 
que os dados sejam altamente disponíveis, mesmo em 
situações em que a consistência imediata não seja possível —
priorizando escalabilidade horizontal e tolerância a falhas.

===== PAGINA 8 =====
Por que NoSQL é essencial no mundo atual?
Aplicações como redes sociais, plataformas de vídeo sob 
demanda, marketplaces globais e sistemas de IoT demandam 
bancos de dados capazes de processar milhões de transações 
por segundo, em tempo real e em múltiplas regiões. O NoSQL
responde a essa demanda ao permitir alta disponibilidade, 
replicação automática, balanceamento de carga e suporte a 
dados não estruturados, como JSON, XML ou até grafos 
complexos de relações entre usuários.

===== PAGINA 10 =====
Tipos de Bancos de Dados NoSQL
Os bancos de dados NoSQL são classificados em quatro categorias 
principais:
• Chave-valor.
• Documentos.
• Colunas.
• Grafos.
Cada tipo adota uma estrutura própria de armazenamento, sendo 
mais adequado para contextos em que o modelo relacional 
tradicional não atende à demanda de escalabilidade ou flexibilidade 
estrutural. A escolha do tipo depende diretamente da natureza dos 
dados e do padrão de acesso.
Exemplo prático: plataformas como Twitter usam bancos chave-
valor para armazenar sessões e contadores, enquanto LinkedIn
adota bancos de grafos para modelar conexões entre usuários.

===== PAGINA 11 =====
Bancos de Dados Orientados a Documentos
Esses bancos armazenam os dados como documentos (JSON, 
BSON ou XML), em que cada entrada pode conter campos 
diferentes e aninhados. Essa estrutura é vantajosa para 
aplicações com esquemas flexíveis.
Tecnologias populares: MongoDB, CouchDB.
Vantagens: consultas ricas por chave e valor, flexibilidade de 
estrutura e indexação eficiente.
Exemplo prático: um sistema de gerenciamento de e-
commerce pode armazenar os dados dos produtos em 
documentos JSON com campos personalizados por categoria 
(ex.: roupas, eletrônicos).

===== PAGINA 12 =====
Bancos Chave-Valor e Orientados a Colunas
Chave-valor: armazenam pares simples, com acesso direto 
por chave.
Exemplo: Redis, usado para armazenar cache e sessões de 
usuários em aplicações web de alta performance.
Aplicação: login de usuários, carrinhos de compras, tokens de 
autenticação.
Colunar: organizam os dados em famílias de colunas, 
permitindo leitura rápida e compressão eficiente.
Exemplo: Apache Cassandra, usado pela Netflix para 
armazenar eventos de reprodução e recomendações.
Aplicação: sistemas de monitoramento, logs e análise de 
séries temporais.

===== PAGINA 13 =====
Bancos Orientados a Grafos
Projetados para armazenar entidades e os relacionamentos 
entre elas, bancos de grafos representam os dados como nós 
(entidades) e arestas (relacionamentos), permitindo consultas 
com alta performance em estruturas altamente conectadas.
Tecnologias populares: Neo4j, ArangoDB, Amazon Neptune.
Exemplo: o algoritmo de sugestões de amizade do Facebook é 
implementado sobre grafos, analisando conexões indiretas e 
interesses em comum.
Aplicação: recomendação de conteúdo, detecção de fraudes, 
análise de redes de transporte ou logística.

===== PAGINA 14 =====
Comparação com Bancos Relacionais
Os bancos NoSQL não substituem os relacionais, mas os complementam em ambientes 
que exigem alta escalabilidade, tolerância a falhas e velocidade de resposta.
Exemplo comparativo:
• MySQL é ideal para um sistema bancário (transações).
• MongoDB ou Cassandra são mais indicados para armazenar os dados de sensores 
em tempo real de uma cidade inteligente.

===== PAGINA 17 =====
Diferenciais técnicos: ACID versus BASE
• ACID (Atomicidade, Consistência, Isolamento e 
Durabilidade) assegura a integridade dos dados em 
transações nos bancos relacionais.
• BASE (Basicamente Disponível, Estado Flexível, Consistência 
Eventual) prioriza desempenho e tolerância a falhas em 
sistemas NoSQL.
Exemplo comparativo:
• Um banco tradicional (ACID) garante que uma transação de 
débito e crédito ocorra integralmente.
• Um app de redes sociais (BASE) pode exibir um novo post a 
um usuário antes que ele esteja visível para todos.

===== PAGINA 18 =====
Escalabilidade: vertical versus horizontal
• SQL escala verticalmente (melhoria de hardware).
• NoSQL escala horizontalmente (adição de servidores).
Exemplo:
• Um sistema ERP rodando em PostgreSQL precisa de mais 
CPU e RAM conforme cresce.
• Um sistema de rastreamento logístico em tempo real, 
rodando com Apache Cassandra, distribui os dados 
automaticamente entre vários nós, mantendo alta 
disponibilidade e baixa latência.

===== PAGINA 19 =====
Casos de uso: quando escolher SQL ou NoSQL
SQL é indicado para: aplicações com forte controle 
transacional, regras de integridade referencial complexas e 
relatórios estruturados (BI, ERP , CRM).
NoSQL é indicado para: aplicações com dados 
semiestruturados ou não estruturados, grandes volumes e 
acesso em alta concorrência e contextos com constante 
evolução do esquema.
Exemplo prático:
• Bancos e instituições financeiras usam Oracle ou MySQL.
• Spotify e Airbnb utilizam NoSQL (Cassandra, Redis, 
MongoDB) para streaming, caching e recomendações.

===== PAGINA 20 =====
Integração híbrida: o melhor dos dois mundos
Em arquiteturas modernas, é comum integrar bancos 
relacionais e não relacionais no mesmo sistema.
Exemplo de arquitetura híbrida:
• Banco relacional (PostgreSQL) para armazenar perfis de 
usuários.
• NoSQL (MongoDB) para armazenar preferências, interações 
e dados de navegação em tempo real.
Essa abordagem garante integridade nos dados críticos e 
flexibilidade nos dados dinâmicos e volumosos.

Por onde começar? 
Adotar um modelo de 
dados flexível com NoSQL:
•Utilizar bancos orientados 
a documentos, chave-

conforme o tipo de dado e 
a necessidade de 
leitura/escrita.
•Eliminar a rigidez de 
esquemas fixos, 
permitindo a adaptação 
ágil do banco às mudanças 
de requisitos.
•Exemplos: MongoDB para 
aplicações web com dados 
semiestruturados; Redis 
para cache de sessões de 
usuário.
Avaliar a escalabilidade 
horizontal:
•Aplicar particionamento 
(*sharding*) para distribuir 
dados entre servidores e 
garantir escalabilidade 
linear.
•Aumentar a capacidade de 
leitura e escrita sem 
comprometer a 
disponibilidade do sistema.
•Exemplos: Cassandra em 
aplicações de 
telecomunicações; 
DynamoDB em 
plataformas de e-
commerce.
Aproveitar a consistência 
eventual com replicação:
•Usar réplicas para garantir 
alta disponibilidade em 
sistemas críticos e reduzir 
latência.
•Garantir consistência dos 
dados com base no 
modelo BASE: Basicamente 
disponível, Estado flexível 
e Consistência eventual.
•Exemplos: Couchbase para 
sistemas com muitas 
requisições simultâneas; 
Neo4j para redes sociais 
com forte volume de 
leitura distribuída.
